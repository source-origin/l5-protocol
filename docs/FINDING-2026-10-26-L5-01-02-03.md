## L5-01 (critical) · `CreditScore` decoded `Agent` as `AgentView`

`CreditScore` declared its own 12-word struct and called `identity.agents(addr)`,
which returns `AgentIdentity.Agent` — a struct that *begins with*
`address agentAddr; uint256 agentId; string handle; string did; …`.

ABI decoding is positional. Word 2 of the return data is therefore a **string
offset pointer**, not `totalSuccessful`. Measured on a freshly registered agent
with zero history:

```
word layout it actually read:
  word 0  uint256(agentAddr << 96)     -> totalRevenue
  word 1  agentId                      -> totalTransactions
  word 2  offset of `handle`           -> totalSuccessful   <-- garbage
  ...
```

Result before the fix: a brand-new agent with no revenue, no transactions and no
contributions scored **10000 / 10000** and was granted the **maximum credit
limit**. The `totalSuccessful` garbage word makes `successRate` saturate, and
every other dimension reads a slot that is not the field it names.

**Root cause:** the comment said "字段视图顺序必须与 AgentIdentity.Agent 逐一对应"
— i.e. the alignment was maintained *by a comment*. It was never true.

**Fix — structural, not a patch:**

1. `src/L5Types.sol` — `AgentView` now has exactly one declaration, imported by
   both producer and consumer. Two look-alike structs can no longer drift.
2. `AgentIdentity.creditView(address)` — the projection is built **field by
   field from storage inside the producing contract**. The compiler, not a
   comment, verifies each assignment against `Agent`.
3. `IAgentIdentity` now exposes `creditView()`; `agents()` is gone from the
   interface. Decoding another contract's storage layout into a locally declared
   struct is now impossible through this path.
4. Defense in depth in `calculateCredit()`:
   `require(a.totalSuccessful <= a.totalTransactions, "CreditScore: inconsistent view")`
   — a self-inconsistent view fails closed instead of minting credit. Pinned by
   `test_Fixed_InconsistentViewReverts` with a deliberately lying mock.

Post-fix behaviour: a fresh agent scores **2600** (neutral 0.5 success rate ×
40% + zero quality + 3000 base stability × 20%), limit 2600. That is a defensible
starting point; 10000 was not.

## L5-02 (high) · `recordContribution()` had no access control

```solidity
function recordContribution(address agentAddr, uint256 quality, uint256 complexity, uint256 timeliness)
    external agentExists(agentAddr)   // <-- that is the entire gate
```

Any address could move any agent's contribution score. Confirmed: a stranger
wrote `totalQuality 0 -> 90` in one call. This feeds `reputationScore`
(by `repParams.contributionClockWeight`) and therefore credit and standing.
Same class as the earlier C3 finding — this function was simply missed when the
rest of the contract was gated.

**Fix:**

- `address public contributionRecorder` + `onlyContributionRecorder` modifier.
- `setContributionRecorder(address)` — `onlyOwner`, emits `ContributionRecorderSet`.
- **Fail-closed:** while unset, every call reverts. There is no default-open state.
- Input guard `Identity_ContributionOutOfRange` for dimensions > 100.

Existing test `test_RecordContribution_RaisesReputation` now calls
`setContributionRecorder(address(this))` first — the test was relying on the
hole, which is exactly why the hole survived.

## L5-02b (found while reproducing L5-02) · clock score always truncated to zero

```solidity
uint256 clockScore = (quality * complexity * timeliness) / 1 ether;
```

Dimensions are on a 0-100 scale. `100 * 100 * 100 = 1e6`; `1e6 / 1e18 = 0`.
So `contributionClockScore` — the *only* field `CreditScore` reads for its
contribution dimension, and the field `_computeReputationScore` weights — **never
moved**, for any contribution, ever. Confirmed: 50 perfect contributions →
`totalQuality = 5000`, `contributionClockScore = 0`.

The reviewer's L5-02 said "L5-01 means the credit limit is not even a faithful
reflection of that score". This is the other half: the score itself was a
constant.

**Fix:** divisor `1000` (so `100/100/100 → 1000`), and the accumulator caps at
`SCORE_MAX`. Pinned by `test_Fixed_RecorderWritesAndClockScoreMoves` and
`test_Fixed_ClockScoreCapsAtMax`.

## L5-03 (medium) · `crossChainSettle()` debited a channel and moved no value

```solidity
ch.balance -= amount;                      // accounting says: paid out
emit CrossChainSettled(...);               // no transfer, no bridge call
// 未来：调用 Axelar / LayerZero / IBC 协议进行实际跨链转账
```

Measured: deposit 5 ether, cross-settle 2 ether → bridge balance **0**, escrow
balance **still 5 ether**, channel balance **3 ether**. The 2 ether is stranded:
nobody can ever claim it, and the channel can no longer settle its real value
(`settleChannel` with a 4-ether cumulative voucher reverts on
`Channel: exceeds balance`). The funds are not stolen, they are **stuck** — and
`finalizeSettlement` refunds only the 3 the accounting believes is left.

Worse: the guard was `ch.sender == msg.sender || ch.receiver == msg.sender`, so
the **receiver** could push the payer's channel funds outward.

**Fix:**

- `address public crossChainBridge` + `setCrossChainBridge` (`onlyOwner`).
- `require(bridge != address(0), "Channel: cross-chain bridge not configured")` —
  fail-closed. A cross-chain path that cannot move value must not pretend to.
- Value moves atomically: `bridge.call{value: amount}("")`, then the emit.
  Effects before interaction, plus `nonReentrant`.
- **Sender-only.** The receiver can no longer initiate an outflow.
- `require(destPayee != address(0))`.

Pinned by five tests, including a solvency invariant: after a cross-chain
settlement, `address(escrow).balance == channels(cid).balance`.

The bridge is a plug, not an implementation: an Axelar/LayerZero/IBC adapter
implements the sink. Until one is configured, the function reverts rather than
silently stranding funds. **This contract is not doing real cross-chain
settlement today, and now it says so instead of appearing to.**

## What each fix has in common

All four are the same failure of imagination: **a comment claimed a property the
code did not enforce, and no test could observe the difference.**

- L5-01: "field order corresponds" — asserted in prose, never in code.
- L5-02: "called by the contribution-clock contract" — a comment, not a modifier.
- L5-02b: `1 ether` divisor — a unit nobody tested at the actual input scale.
- L5-03: "future: call Axelar" — a TODO that shipped as a balance mutation.

The regression suite tests the *observable consequence* of each property (a fresh
agent's score, a stranger's revert, a clock score that moves, an ETH balance that
matches the ledger), not the property's description.
